If you only remember three things: (1) every run is client-only - an HTTP client can never see server CPU/RAM, and v2 never estimates it (archived v1 runs aside); (2) every run produces one results.json from raw.jsonl + self-monitor samples, and nothing is invented; (3) the language comparison and the HTTP load test answer different questions - never compare their numbers.

One host, one HTTP boundary. An external client can never see server CPU, RAM or OOM events - and v2 never pretends otherwise.

Developer notes - 01 - System context

  • heavyload/http_client.py owns make_connection() and one-shot probe(); the load generator never uses anything else to reach the target.
  • samplers.SamplerSet runs exactly two daemon threads: the 1 Hz health probe and the generator self-monitor (generator_series: CPU% from process_time deltas, working set via ctypes psapi / procfs). Always client_only=True.
  • The generator self-monitor observes THIS process only - it never crosses the HTTP boundary. Server CPU / RAM / OOM stay invisible and are never estimated; those SLOs grade N/A - insufficient evidence.
  • runner.preflight() performs 4 read-only checks: target reachable, health endpoint, vantage point (loopback vs remote), host RAM headroom.
  • scripts/native_target.py <site-id> start|stop|status manages local targets natively (os.spawnve, PID records under runs/targets/) - no shell, no SDK.

Entry points, one runner, the v2 analysis stack (quality, scalability, suitability), one result document. Dashed boxes are optional.

Developer notes - 02 - Module architecture

  • runner.run_benchmark(cfg, root, log, preflight_result, bench_holder) is the SINGLE orchestrator - cli.py and server.py /api/run/start both call it, so a feature added there works in both UIs.
  • engine.Benchmark.run() returns the results{} dict and records step_windows (one window per concurrency level); grading.grade() adds adjudication, quality.check_run() + scalability.analyze() attach their blocks, schema.ensure_current() adds v2 identity fields.
  • runtime_comparison.run() + suitability.build() are wrapped in try/except: any exception becomes status=error + a warning in results.json, never a lost run.
  • comparison_sources/ is the language registry: one module per language (14 total); adding a module = adding a language. procmetrics.py measures child RSS + CPU time (Windows GetProcessMemoryInfo/GetProcessTimes, POSIX wait4 rusage) or returns None - unavailable, never estimated.
  • report.build() emits one self-contained HTML (16 sections, inline SVG, no JS); paths.SAFE_ARTIFACTS is the whitelist used by server.py for /runs/<run-id>/<artifact>.

Eight orchestration steps and the eight HTTP phases. The language comparison deliberately runs last.

Developer notes - 03 - One run, start to finish

  • config.preset_phases(name) returns the 8 phases; profiles only change durations + ceilings (smoke ~33 s C=20, quick ~3.5 min C=100, heavy ~5.5 min C=200, stress ~10.5 min C=400, standard ~24 min C=300).
  • engine._run_phase() drives one phase, _worker() issues requests, _writer() appends one JSON line per request to raw.jsonl, _guard_check() can set _set_abort(reason).
  • Guardrails come from config.guardrails: max_anon_mib (generator working-set ceiling), min_host_free_gb, max_error_rate_pct, max_consecutive_failures. On abort, cooldown_s + reprobe_s still run, partial results are written and the run is graded right-censored.
  • Step 7 sits after ensure_current() on purpose - the HTTP result is already aggregated, graded and quality-checked before a single language program is spawned.

Every published number traces back to a raw line, a self-monitor sample or a verified checksum.

Developer notes - 04 - Data flow: raw bytes to verdict

  • engine._aggregate_requests() -> metrics.http (see schema/metrics.py empty_http()); _aggregate_samples() -> metrics.resources. Server-side keys stay None (shown as unavailable); generator-side keys (gen_cpu_*, gen_rss_*) are measured.
  • grading.grade() registers S1-S9; in client-only runs S5/S6/S8 grade N/A because server memory/stability is not observable - the tool never invents evidence.
  • schema/migrate.py performs an ADDITIVE v1 -> v2 migration: no v1 key is deleted, renamed or coerced, so archived reports still render.
  • quality.check_run() labels every check ok / warn / fail / insufficient_evidence; scalability.analyze() reports insufficient_evidence below two measured concurrency levels.
  • Writes go through util.atomic_json(); report.py draws inline SVG charts from the same dict - no second data source, no estimates.

v2 comparability: only runs measured under conditions that can be proven equal may be ranked.

Developer notes - 05 - Modes and the comparability gate

  • schema/metrics.py:can_compare(a, b) requires equal benchmark_mode, visibility, schema_version and workload_class; plain client_only (remote target) is then refused outright.
  • client_only_same_host additionally requires equal generator_fingerprint (hostname|platform|machine|cpu_count) and target_host - archived runs without the fingerprint are refused.
  • VISIBILITY_LEVELS = ("full_server", "client_only", "client_only_same_host", "server_via_adapter"); archived docker_lab (v1) runs keep full_server and compare only among themselves - that instrumentation no longer exists.
  • compare.py sets comparable=False + a reason and still returns raw rows; report_compare.py prints NOT COMPARABLE instead of a leaderboard. A refusal reason is always shown, never silently dropped.
  • server_via_adapter is a declared seam, not an implementation: add a RuntimeAdapter (heavyload/adapters/) and its outputs stay labelled separately.

Pinned workloads, 14 languages via the registry, one checksum gate, no simulated numbers.

Developer notes - 06 - Language runtime comparison

  • runtime_comparison.py pins 5 workloads (PRIME_N, JSON_ROWS/ROUNDS, MAP_KEYS/ROUNDS, TEXT_ROWS, MATMUL_N) and the EXPECTED checksum dict. Change a constant and you MUST recompute EXPECTED or every variant is rejected.
  • comparison_sources/ registers 14 languages (Spid3r, Python, JavaScript, TypeScript, PHP, Ruby, Java, Kotlin, Go, C#, Swift, Rust, C, C++); each module declares TOOL_KEYS, build steps and run variants. Workload B exists only where the stdlib ships a JSON serializer (not applicable elsewhere).
  • Each generated program prints exactly two lines: RESULT <a> <b> and TIME_US <n>; _parse_output() enforces that contract.
  • detect_tools() probes host toolchains; missing ones are skipped with a warning. procmetrics adds OS-measured peak working set + CPU time per variant (or honest unavailable).
  • cli.py --verify-sources compiles + runs every detected toolchain against the pinned checksums and prints the table. Stats: median, stdev, CV%, IQR, t-CI + bootstrap CI; slowdown ratios + pairwise geomean matrix.

Invariants & gotchas

Rules that are easy to break and expensive to debug. Treat these as the project's contract.

  1. Stdlib only - No pip install for the core. Optional extras (psutil, Playwright) are never required; the CDP client uses plain socket.
  2. Nothing fabricates evidence - Missing toolchains degrade to unavailable / not applicable; checksum-mismatched comparison variants are REJECTED, never published; quality checks can answer insufficient_evidence.
  3. Client-only vantage - Server CPU / RAM / OOM is never estimated from the outside; S5 / S6 / S8 grade N/A - insufficient evidence instead of a fake PASS.
  4. Additive schema - v1 keys are never deleted, renamed or coerced - archived reports keep rendering.
  5. Visibility is explicit - can_compare() refuses cross-vantage and cross-host rankings with a stated reason; client_only_same_host is a single-host client-side comparison, not a server-resource benchmark.
  6. Instrumentation must not perturb - The sampler stack is two daemon threads; the generator's own CPU/memory is measured so client-side saturation can never hide.
  7. No simulated numbers - Workload constants are pinned; --verify-sources re-proves every toolchain; noisy (CV > 15%) variants are flagged, not hidden.
  8. Compute speed is not HTTP throughput - The language comparison measures in-process milliseconds; RPS / p99 come from the HTTP load test. Never compare the two.
  9. Comparison is failure-safe - It runs AFTER the HTTP schedule; an exception becomes a warning in results.json and the load result survives.
  10. Coordinated omission is handled - Percentiles carry the as_scheduled_latency view; generator dispatch lag is measured separately so client scheduling delay is never blamed on the target.
  11. Spid3r specifics - Only now_ms() (1 ms resolution); JSON builtin is json_write, not json_encode. The deployed store still runs the tree-walk engine, the slowest of the measured variants.

Glossary

Terms that appear in results, reports and code reviews.

TermMeaning
